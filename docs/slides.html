Ajax API: Evolution & Pain Points

A brief history
Drupal 7 Ajax API unified into a single core framework
Drupal 8 → 11 Rebuilt on Symfony's HttpKernel - AjaxResponse extends JsonResponse; interactions become a stack of Commands

Mature. Well-documented. Everywhere in core - exposed filters, autocomplete, modals, inline entity forms.

The right answer for 2011.

The mechanics
01An element gets an #ajax property - callback, wrapper, event
02The callback returns an AjaxResponse built from one or more Commands
03core/drupal.ajax runs each command client-side; Drupal.behaviors re-attach to the new markup

Section 03 · The Reveal

That's not a hypothetical.

It's called HTMX.

Built on an idea older than Ajax: hypermedia.

The idea

You already know hypermedia. Every <a href> and every <form> you've ever written is a hypermedia control - an element that tells the browser what to fetch and where to put the result. HTMX just extends that vocabulary: any element, any event, any HTTP verb, any part of the page as the target.

In code
<select hx-get="/filter-results"
        hx-trigger="change"
        hx-target="#results"
        hx-swap="innerHTML">
  ...
</select>

<div id="results">
  <!-- server returns just this fragment -->
</div>

One element. Four attributes. The behavior lives right there in the tag - no PHP file to go find, no wrapper ID to keep in sync across two files.

The request/response cycle

sequenceDiagram
    participant U as User
    participant B as Browser htmx.js
    participant S as Server

    U->>B: Triggers hx-trigger event (change)

Same three participants - user, browser, server. Seven steps in the Ajax version. Four here.

The bigger idea

The response is the next state of the UI - already rendered.

No separate JSON API. No client-side templating layer. HTMX just closes the gap between the first page load and everything after, so both work the same way.

Four attributes
Verbhx-get / hx-post / hx-put / hx-delete
Triggerhx-trigger - any DOM event, not just click/submit
Targethx-target - any element, not just the one that triggered this
Swaphx-swap - innerHTML, outerHTML, beforeend, afterbegin, and more
Coming up

HTMX gives Drupal back a vocabulary it never lost - hypermedia.

Section 04 · 8 min
04

Mapping HTMX onto Drupal's Architecture

The question

HTMX doesn't need anything special from Drupal. It needs three things Drupal already has - and has had for over a decade.

Routing
my_module.filter_results:
  path: '/filter-results'
  defaults:
    _controller: '\Drupal\my_module\Controller\FilterController::results'
  requirements:
    _access: 'TRUE'
  options:
    _htmx_route: TRUE

hx-get="/filter-results" isn't a special Ajax callback. It's a normal Drupal route with one flag: _htmx_route returns just the main content and its assets, not the whole themed page.

Render arrays
public function results(Request $request) {
  $filter = $request->query->get('filter');
  return [
    '#theme' => 'item_list',
    '#items' => $this->getFilteredItems($filter),
    '#cache' => [
      'tags' => ['node_list'],
      'contexts' => ['url.query_args:filter'],
    ],
  ];
}

The same render array every Drupal controller already returns. No AjaxResponse. No Commands. The render pipeline already builds exactly this.

Core does the glue
use Drupal\Core\Htmx\Htmx;

(new Htmx())
  ->get(Url::fromRoute('my_module.filter_results'))
  ->trigger('change')
  ->target('#results')
  ->swap('innerHTML')
  ->applyTo($form['filter']);

The same four attributes from §3, built in PHP. applyTo() attaches core/drupal.htmx, which loads the response’s assets and re-attaches Drupal.behaviors after every swap.

Where this pays off
Ajax APIAn AjaxResponse built from Commands doesn't sit in the cache pipeline. You're mostly on your own.
HTMXA plain render array - cache tags bubble up, contexts vary the response automatically. Caching for free.
Recap
HTMX asks forDrupal already has
A URL (hx-get/hx-post)A route + controller (_htmx_route)
HTML to swap inA render array
Correctness under caching#cache tags & contexts

Three things Drupal already gives every page. HTMX just asks for them directly - no translation layer in between.

06

Ajax API vs HTMX, Compared Honestly

DX & Performance

DX

Ajax APIMore ceremony - but the most proven path for complex multi-step forms and wizards.
HTMXFar less ceremony. 11.3 rebuilds forms from HTMX requests, but complex multi-step flows are less proven.

Performance

Ajax APIJSON command stack, run command by command in the browser.
HTMX~16kb library; the response is the HTML itself. Up to 71% less JS loaded, per drupal.org.
Debugging & Progressive Enhancement

Debugging

Ajax APINetwork tab shows an opaque command stack. Wrapper-ID typos fail silently.
HTMXNetwork tab shows the literal HTML that got inserted. What you see is what you got.

Progressive enhancement

Both layer JS onto a real form/link element the same way. Honestly? Close to a wash - neither gets tested with JS off in most real projects.

The verdict, side by side
Ajax APIHTMX
DXMore ceremony, most proven for complex multi-step formsLess ceremony, multi-step patterns still maturing
PerformanceJSON command stack, executed client-sideSmall library, HTML response, up to 71% less JS
DebuggingOpaque command stack, silent failuresTransparent - see the actual HTML
Progressive enhancementBuilt on the same fallback pattern in both - rarely tested either way
The take

Pick the tool for the job, not the trend.

HTMX where round trips are simple and the UI is a fragment. Ajax API where it already works, and for complex multi-step flows - for now. This isn't a replace-everything story.

07

Incremental Adoption Strategy

No rewrite required

You don't rip out the Ajax API to start using HTMX. They coexist on the same page - HTMX doesn't touch anything #ajax owns.

Already in core
// Using the Htmx class? It attaches core/drupal.htmx for you.
// Hand-writing hx-* attributes in Twig? One line:
$build['#attached']['library'][] = 'core/drupal.htmx';

Drupal 11.3+ ships core/htmx and core/drupal.htmx. No library definition, no CDN, no build step.

Pick candidates, don’t do a sweep
Leave itExisting Ajax API code that already works. No sweep, no module-wide rewrite.
HTMX candidatesNew interactive spots, or the small annoying ones - a filter, a load-more pager, an autocomplete list.
<nav hx-boost="true">

A low-effort on-ramp: links and forms inside become HTMX requests. Start with one region - each boosted request still swaps the whole <body>, so test page-level JS like the toolbar.

The rule of thumb
New interactive featureHTMX by default.
Existing, working Ajax API codeLeave it alone.
Complex multi-step formsWizards, heavy Form API flows - keep them on the Ajax API for now, per §6’s verdict.
The take

A second tool in the same box, not a rewrite.

Use what core ships, pick a handful of low-risk candidates, boost one region to get a feel for it. No migration weekend required.

Current Status + How to Contribute

Where things stand today

This isn’t a someday story - HTMX arrived in core in 11.2 and became fully featured in 11.3, as part of an active initiative to replace the Ajax system.

Core initiative“Replace AJAX API with HTMX” - an official community initiative, still active. Both APIs run side by side until contrib has time to convert.
Contrib moduledrupal/htmx adds extra tooling on top of core - 1,156 sites already using it.

Up to 71% less JavaScript loaded for browser-server interactions with native HTMX, per drupal.org.

Both APIs, on purpose

Same incremental philosophy as §7 - just scaled up to core. Full deprecation waits until contrib has had real time to convert.

Experience BuilderPage/layout building - not interaction plumbing.
Single Directory ComponentsComponent authoring - not interaction plumbing.
How to contribute

It’s not waiting on permission.

Already in core, actively being worked, and it needs hands. On 11.3? Convert one #ajax callback and see how it feels.
